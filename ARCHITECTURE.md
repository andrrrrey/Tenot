# Tenot — описание проекта и архитектуры

> Документ написан простым языком и объясняет, **что это за проект**, **из чего он состоит**,
> **как устроен внутри** и **почему приняты именно такие технические решения**.

---

## 1. Что такое Tenot

**Tenot** — это сайт объявлений (по сути аналог Авито/OLX), сделанный пока в формате MVP
(минимально работающего продукта). Пользователи могут:

- регистрироваться и входить в аккаунт;
- размещать объявления о продаже (с фото и видео, ценой, городом, категорией);
- для автозапчастей — указывать марку, модель и год машины;
- искать и фильтровать объявления (по категории, цене, городу, авто, с исправлением опечаток);
- добавлять объявления в избранное;
- общаться с продавцом в чате (текстом и голосовыми сообщениями);
- оставлять отзывы о других пользователях;
- редактировать профиль и аватар.

Отдельно есть **админ-панель**: управление пользователями (роли), объявлениями, категориями
и модерация отзывов.

Проект ориентирован на русскоязычную аудиторию (интерфейс на русском, домены `tenot.ru` / `tenor.ru`).

## 2. Технологии (стек) одним списком

| Слой | Технология | Зачем |
|------|-----------|-------|
| Фронтенд | **Next.js 15** (App Router) + **React 19** | Современный фреймворк с серверным рендерингом и встроенным API-слоем |
| Состояние на клиенте | **Zustand** | Очень лёгкое хранилище состояния (пользователь, избранное) без громоздкого Redux |
| Бэкенд | **NestJS 10** (Node.js + TypeScript) | Структурированный фреймворк с модулями, удобен для роста проекта |
| База данных | **PostgreSQL 16** | Надёжная реляционная СУБД |
| Работа с БД | **Prisma ORM** | Типобезопасный доступ к данным + миграции схемы |
| Авторизация | **JWT** + **bcryptjs** + **Passport** | Токены в httpOnly-cookie, безопасное хранение паролей |
| Веб-сервер / прокси | **Nginx** | SSL, реверс-прокси, кэш статики, защита и ограничение нагрузки |
| Инфраструктура | **Docker + docker-compose** | Одинаковый запуск локально и на сервере |

Везде используется **TypeScript** — и на фронте, и на бэке. Это даёт единый язык и
меньше ошибок за счёт типизации.

## 4. Общая архитектура: как всё связано

Это классическая **трёхзвенная архитектура** (фронт → API → база данных), но с одной важной
особенностью — **браузер никогда не ходит на бэкенд напрямую**. Все запросы идут через Next.js.

```
                      ┌─────────────────────────────────────────────────┐
   Браузер  ──HTTPS──▶│                    NGINX                         │
  (телефон/ПК)        │   SSL, кэш статики, rate-limit, защита           │
                      └───────────────┬─────────────────────────────────┘
                                      │
                       ┌──────────────▼───────────────┐
                       │   Next.js (web, порт 3000)    │
                       │  • рендерит страницы          │
                       │  • /api/auth/* — логин/cookie │
                       │  • /api/proxy/* — прокси       │
                       └──────────────┬────────────────┘
                                      │ внутренняя docker-сеть
                       ┌──────────────▼────────────────┐
                       │   NestJS (api, порт 3001)     │
                       │  • вся бизнес-логика          │
                       │  • Prisma                      │
                       └──────────────┬────────────────┘
                                      │
                       ┌──────────────▼────────────────┐
                       │   PostgreSQL (db, порт 5432)   │
                       └────────────────────────────────┘
```

### Почему браузер не ходит на бэкенд напрямую?

Это ключевое архитектурное решение. У него несколько причин:

1. **Безопасность токена.** JWT-токен хранится в **httpOnly-cookie** — браузерный JavaScript
   его не видит и не может украсть (защита от XSS-атак). Когда нужно сходить на бэкенд,
   запрос идёт на `/api/proxy/...`, а серверный код Next.js сам достаёт токен из cookie и
   подставляет его в заголовок `Authorization`. Подробности — в `frontend/app/api/proxy/[...path]/route.ts`.

2. **Бэкенд можно полностью спрятать.** API-контейнер не обязан смотреть в интернет — он
   доступен только внутри docker-сети. Снаружи виден только Nginx.

3. **Единый origin.** Браузер общается только с одним доменом, поэтому нет проблем с CORS и
   нет утечки внутренних адресов.

## 5. Фронтенд (Next.js) подробнее

### App Router и серверный рендеринг
Используется новый **App Router** Next.js (папка `app/`). Страницы могут быть серверными или
клиентскими (`"use client"`). Многие интерактивные страницы (поиск, чат, карточка товара) —
клиентские, потому что им нужно состояние и события пользователя.

### Три типа кода во фронте
1. **Страницы** (`app/.../page.tsx`) — то, что видит пользователь.
2. **API-роуты** (`app/api/...`) — серверный код, который работает на сервере Next.js:
   - `api/auth/login|register|logout|me` — управляют входом и cookie;
   - `api/proxy/[...path]` — универсальный «туннель» ко всем эндпоинтам бэкенда.
3. **services/** — тонкие функции на клиенте, которые просто дёргают `/api/proxy/...`
   (например, `services/listings.ts`, `services/chat.ts`).

### Слой работы с API (`lib/api.ts`)
Здесь единая обёртка `api.get/post/patch/del/upload` с **централизованной обработкой ошибок**.
Особенно важна обработка `401/403`: при ошибке авторизации срабатывает глобальный обработчик
из `AuthProvider`, который разлогинивает пользователя и перекидывает на `/login`. Это решает
типовую проблему «протух токен — а приложение этого не заметило».

### Состояние (Zustand, `lib/store.ts`)
Глобальное состояние минимальное: текущий пользователь, избранное, локальные товары. Выбран
**Zustand**, а не Redux, потому что проекту не нужна тяжёлая инфраструктура — достаточно
простого и быстрого стора в несколько строк.

### Загрузка пользователя при старте (`AuthProvider`)
При открытии сайта `AuthProvider` дёргает `/api/auth/me`, узнаёт, кто залогинен, и кладёт
данные в стор. Если не залогинен — это нормально, просто гость.

### middleware.ts — интересный «костыль» с пользой
Проект **не использует** Server Actions, но после передеплоя старые вкладки в браузере могут
слать POST-запросы со стухшим заголовком `Next-Action`, что вызывает ошибку. Middleware ловит
такие запросы и делает редирект на ту же страницу — браузер перезагружается и подтягивает свежий
код. Это пример прагматичного решения реальной production-проблемы.

### Загрузка файлов и `/uploads`
Картинки и видео объявлений хранятся на стороне бэкенда (папка `uploads`). Next.js через
`rewrites` в `next.config.mjs` пробрасывает путь `/uploads/...` напрямую на API, чтобы файлы
отдавались без лишних прослоек.

## 6. Бэкенд (NestJS) подробнее

### Модульная структура
NestJS строится из **модулей** — по одному на бизнес-сущность: `auth`, `listings`, `chat`,
`favorites`, `reviews`, `categories`, `cities`, `car-makes`, `users`, `admin`. Каждый модуль
обычно содержит:

- **controller** — описывает HTTP-маршруты (что приходит снаружи);
- **service** — бизнес-логика и работа с базой через Prisma;
- **dto** — описание и валидация входных данных.

Такое разделение делает код предсказуемым: всегда понятно, где искать логику конкретной функции.

### Безопасность по умолчанию: «всё закрыто, пока не открыли»
В `app.module.ts` два глобальных guard'а (охранника) включены сразу для всего приложения:

```ts
{ provide: APP_GUARD, useClass: JwtAuthGuard }   // проверяет токен
{ provide: APP_GUARD, useClass: RolesGuard }     // проверяет роль
```

Это значит: **по умолчанию любой эндпоинт требует авторизации**. Чтобы открыть что-то публично,
на метод вешают декоратор `@Public()` (например, просмотр объявлений и категорий). А чтобы
ограничить по роли — `@Roles('ADMIN')`. Это безопасный подход «secure by default»: забыть
закрыть эндпоинт нельзя, можно только осознанно открыть.

### Как работает вход и токены
1. Пароль при регистрации хешируется через **bcrypt** (`auth.service.ts`) — в базе пароли в
   открытом виде не хранятся.
2. При входе бэкенд возвращает `access_token` (JWT с `sub` = id пользователя и `role`).
3. Фронт (`api/auth/login`) кладёт этот токен в **httpOnly-cookie** на 30 дней.
4. На каждый защищённый запрос `JwtStrategy` проверяет токен и подгружает пользователя из БД,
   чтобы убедиться, что он ещё существует.

### Валидация входных данных
В `main.ts` включён глобальный `ValidationPipe` с `whitelist: true` — это значит, что лишние
поля из запроса отбрасываются, а данные проверяются по DTO. Защищает от мусорных и вредных полей.

### Таймауты и стабильность соединений
Здесь видно внимание к продакшен-деталям:
- `TimeoutInterceptor(30s)` — обрывает зависшие запросы;
- `server.keepAliveTimeout = 65s` (в `main.ts`) специально больше, чем у Nginx — иначе
  возникают ошибки «connection reset». Это типичная, но часто забываемая настройка для связки
  Node.js + Nginx.

## 7. База данных и модель данных

Схема описана в `backend/api/prisma/schema.prisma`. Основные сущности:

- **User** — пользователь (email, хеш пароля, имя, телефон, аватар, роль USER/ADMIN, город).
- **Listing** — объявление (заголовок, артикул, описание, цена, статус PUBLISHED/DRAFT, флаг
  активности, связи с категорией, городом, авто).
- **ListingImage** — фото/видео объявления (с порядком и пометкой «обложка»).
- **Category** — категория, древовидная (через `parentId` → подкатегории). Флаг `hasCarFilter`
  включает фильтр по авто для автозапчастей.
- **City** — город/регион/район, тоже **самоссылающееся дерево** (`regionId`): регион → города →
  районы.
- **CarMake / CarModel** — марки и модели машин (с поколениями и годами выпуска) для автофильтра.
- **Chat / Message** — переписка. Чат привязан к объявлению и паре «инициатор ↔ владелец».
  Сообщение может быть текстом или голосом (`audioUrl`, `audioDuration`), есть отметка «прочитано».
- **Favorite** — избранное (уникальная пара пользователь+объявление).
- **Review** — отзыв (рейтинг, что понравилось/не понравилось, статус модерации
  PENDING/APPROVED/REJECTED, один отзыв на пару автор→получатель).

### Почему деревья через самоссылку?
И категории, и города реализованы как дерево внутри одной таблицы (поле ссылается на ту же
таблицу). Это гибко: можно добавлять любую вложенность (регион → город → район; категория →
подкатегория) без отдельных таблиц на каждый уровень.

### Миграции
В папке `migrations/` — **18 миграций**, и по их названиям видно, как эволюционировал продукт:
от базовой схемы (`init`) к городам и регионам, районам, аватарам, медиа в объявлениях,
голосовым сообщениям, отзывам, автофильтрам и поколениям машин. Миграции — это «история
изменений» базы: на сервере применяются командой `prisma migrate deploy`, что гарантирует
одинаковую структуру БД везде.

## 8. Отдельные интересные решения

### Поиск с исправлением опечаток (без внешнего поисковика)
В `listings.service.ts` реализован **fuzzy-поиск** на чистом коде: алгоритм расстояния
Левенштейна. Логика умная и экономная:
1. Сначала пробуем обычный поиск по подстроке — если что-то нашли, исправлять нечего.
2. Если нет — берём ~300 свежих заголовков, строим словарь слов с частотами.
3. Для каждого слова запроса ищем ближайшее по написанию слово (с поправкой на длину) и отдаём
   предпочтение более частым словам.
4. **Проверяем**, что исправленный запрос реально что-то находит, и только тогда предлагаем его.

Почему так? Это даёт пользователю «вы имели в виду…» без подключения тяжёлого Elasticsearch —
дёшево и достаточно для MVP.

### Чат на «опросе» (polling), а не на WebSocket
Чат обновляется простым опросом: сообщения каждые 3 секунды, список чатов — каждые 10 секунд
(`ChatClient.tsx`). Это проще в разработке и эксплуатации, чем WebSocket-инфраструктура, и для
объёмов MVP полностью достаточно. Логичный размен «простота вместо мгновенности».

### Защита и производительность на уровне Nginx
Конфиг `infra/nginx/conf.d/site.conf` показывает зрелый подход к проду:
- **SSL** (Let's Encrypt), редирект HTTP → HTTPS;
- **rate limiting** (ограничение числа запросов с одного IP);
- блокировка ботов и пустых User-Agent;
- **immutable-кэш** для хешированных статик-файлов `/_next/static/` (можно кэшировать вечно,
  потому что в имени файла есть хеш содержимого);
- keep-alive к Next.js и грамотные таймауты;
- скрытие заголовка `WWW-Authenticate`, чтобы Chrome не показывал нативное окно логина.

### Один способ запуска — Docker
И локально, и на сервере проект поднимается через docker-compose. Контейнеры: `db`, `api`,
`web`, `nginx`. У каждого настроены **healthcheck'и** и зависимости (`web` стартует только после
того, как `api` здоров, а `api` — после `db`). Это устраняет классическую проблему «приложение
поднялось раньше базы». Данные БД и загруженные файлы хранятся в **именованных volume'ах**, то
есть переживают перезапуск контейнеров.

## 9. Как это запустить

**Локально (нужен Docker):**
```bash
docker compose -f docker-compose.local.yml up
# открыть http://localhost:8080
```

**На сервере (прод):** подробно описано в `README_DEPLOY.md` — настройка `.env` (главное —
сменить `JWT_SECRET`), запуск `docker compose up -d --build`, применение миграций, выпуск SSL,
защита `/admin` через basic-auth, бэкапы и автообновление сертификатов.

## 10. Краткие выводы по архитектуре

- **Чёткое разделение слоёв.** Фронт (Next.js) ↔ API (NestJS) ↔ БД (Postgres) — каждый отвечает
  за своё.
- **Безопасность на первом месте.** httpOnly-cookie вместо токена в JS, всё закрыто по умолчанию,
  пароли хешируются, валидация входных данных, защита на Nginx.
- **Прагматичная простота.** Где можно — выбраны лёгкие решения (Zustand вместо Redux, polling
  вместо WebSocket, свой fuzzy-поиск вместо Elasticsearch). Это правильный выбор для MVP: меньше
  движущихся частей — меньше точек отказа.
- **Готовность к проду.** Healthcheck'и, таймауты, rate limiting, кэш статики, миграции,
  бэкапы — всё это говорит о том, что проект рассчитан на реальную эксплуатацию, а не только на
  демонстрацию.
- **Единый TypeScript** на фронте и бэке снижает порог входа и количество ошибок.

Проект — крепкий MVP с продуманной, расширяемой архитектурой, в котором осознанно выбрана
простота там, где сложность пока не нужна.
